# i18n 开发说明

> 更新说明
>
> `src/app/admin/**` 和 `src/app/teacher/**` 已经不再维护单一的 `admin.json` / `teacher.json`。
> 现在按 section 拆分文件，例如：
>
> - `public/locales/zh-CN/admin-home.json`
> - `public/locales/zh-CN/admin-teaching.json`
> - `public/locales/zh-CN/teacher-layout.json`
> - `public/locales/zh-CN/teacher-dashboard.json`
>
> 运行时会按页面按需加载这些拆分文件，并合并回 `admin` / `teacher` namespace。
> 下文如果还出现 `teacher.json` / `admin.json` 的旧表述，以本说明为准。

这份文档给本项目的前端同事用。

目标只有一个：你在改页面时，不需要先研究半天国际化实现，照着这份说明改，就能把文案正确接进来。

如果你只想看最短版本，先看下面这段。

## 30 秒上手

先判断你改的是哪一类页面：

- 如果你改的是 `src/app/teacher/**` 下的教师端页面：
  - 用 `teacher` 命名空间
  - 改对应 section 文件，例如 `public/locales/zh-CN/teacher-dashboard.json`
  - 英文同步改对应 `public/locales/en/*.json`
  - 组件里用 `useTranslation('teacher')`

- 如果你改的是 `src/app/admin/**` 下的管理端页面：
  - 用 `admin` 命名空间
  - 改对应 section 文件，例如 `public/locales/zh-CN/admin-home.json`
  - 英文同步改对应 `public/locales/en/*.json`
  - 组件里用 `useTranslation('admin')`

- 如果你改的是 `src/pages/**` 下的老页面：
  - 优先复用已有命名空间，比如 `common`、`account`、`chat`
  - 去对应的 `public/locales/{语言}/{命名空间}.json` 补文案
  - 组件里用 `t('common:xxx')` / `t('account:xxx')`

- 如果你要新增一个全新的命名空间：
  - 新增 3 份翻译文件：`zh-CN`、`en`、`zh-Hant`
  - 同步改：
    - `public/locales/constants.ts`
    - `public/locales/i18next.d.ts`
    - `src/web/common/i18n/index.ts`

## 当前项目的 i18n 结构

这个项目现在不是一套国际化跑全站，而是两套。

### 1. 教师端 `app` 路由

适用范围：

- `src/app/teacher/**`

入口文件：

- `src/app/teacher/components/TeacherI18nProvider.tsx`

特点：

- 只服务教师端
- 当前只支持 `zh-CN` 和 `en`
- 默认语言是 `zh-CN`
- 语言状态保存在 `localStorage.i18nextLng`
- 顶部导航已经带语言切换

当前翻译文件：

- `public/locales/zh-CN/teacher-*.json`
- `public/locales/en/teacher-*.json`

### 2. 老的 `pages` 路由

适用范围：

- `src/pages/**`
- 大部分历史页面

入口文件：

- `src/web/common/i18n/index.ts`

特点：

- 当前支持 `zh-CN`、`en`、`zh-Hant`
- 使用 `public/locales/{语言}/{命名空间}.json`
- 命名空间要在代码里注册，否则会出现 key 找不到或者类型不完整

相关注册文件：

- `public/locales/constants.ts`
- `public/locales/i18next.d.ts`
- `src/web/common/i18n/index.ts`

## 先学会判断：你该用哪套

最简单的判断方式是看文件路径。

### 走教师端方案

这些路径都按教师端方案处理：

- `src/app/teacher/components/**`
- `src/app/teacher/login/**`
- `src/app/teacher/(layoutPage)/**`

### 走老页面方案

这些路径都按老页面方案处理：

- `src/pages/account/**`
- `src/pages/chat/**`
- `src/pages/dashboard/**`
- `src/pages/dataset/**`
- `src/pages/login/**`

### 不要混用

最容易犯的错是：

- 在教师端组件里去写 `t('common:xxx')`
- 在老页面里去写 `useTranslation('teacher')`

这两种都不推荐。

教师端就用 `teacher`，老页面就走原来的 namespace 体系。

## 教师端开发流程

这是最常见、也是当前最推荐的流程。

### 第 1 步：把文案加到 `teacher.json`

例如你在教师端新增一个“导出成绩”按钮。

先改中文：

```json
{
  "scores": {
    "export": "导出成绩"
  }
}
```

再改英文：

```json
{
  "scores": {
    "export": "Export Scores"
  }
}
```

建议按业务聚合 key，不要平铺一堆零散字段。

推荐这种结构：

```json
{
  "scores": {
    "title": "成绩管理",
    "export": "导出成绩",
    "empty": "暂无成绩数据"
  }
}
```

不推荐这种结构：

```json
{
  "exportScoresButtonText": "导出成绩",
  "scoresPageEmptyText": "暂无成绩数据"
}
```

### 第 2 步：在组件里取文案

教师端组件统一这样写：

```tsx
'use client';

import { useTranslation } from 'react-i18next';

export default function ScoresPage() {
  const { t } = useTranslation('teacher');

  return <button>{t('scores.export')}</button>;
}
```

### 第 3 步：确认是不是客户端组件

`useTranslation('teacher')` 是 React Hook。

所以：

- 用它的组件必须是 Client Component
- 文件顶部一般要有 `'use client';`

如果你当前文件是 Server Component，有两个常见处理方式：

- 把需要文案的那一小块拆成子 Client Component
- 或者先把当前组件改成 Client Component

优先推荐第一种，影响范围更小。

### 第 4 步：本地切换中英文自测

教师端顶部导航已经有语言切换。

你要检查：

- 中文显示是否正常
- 英文显示是否正常
- 刷新页面后语言是否保持
- 新文案是否存在截断、溢出、换行异常

## 老页面开发流程

如果你改的是 `src/pages/**` 下的页面，按这套来。

### 第 1 步：先判断复用哪个 namespace

不要先想着“新建一个 json 文件”。

优先复用已有 namespace。

当前常见 namespace：

- `common`
- `login`
- `app`
- `chat`
- `dataset`
- `workflow`
- `user`
- `account`
- `account_team`
- `account_bill`
- `account_apikey`
- `account_inform`
- `account_info`
- `account_model`
- `account_promotion`
- `account_setting`
- `account_thirdParty`
- `account_usage`
- `dashboard_evaluation`
- `dashboard_mcp`
- `file`
- `publish`
- `teacher`

经验上：

- 很通用的按钮、状态、提示语，放 `common`
- 业务页面自己的标题、说明、模块文案，放对应业务 namespace

### 第 2 步：补翻译文件

例如你要给 `account` 模块新增一个文案：

- `public/locales/zh-CN/account.json`
- `public/locales/en/account.json`
- `public/locales/zh-Hant/account.json`

三份都要补。

如果只补中文，其他语言下会直接缺词。

### 第 3 步：组件里使用

老页面常见写法：

```tsx
import { useTranslation } from 'react-i18next';

export default function Demo() {
  const { t } = useTranslation();

  return <div>{t('account:profile.title')}</div>;
}
```

也可以显式写 namespace：

```tsx
const { t } = useTranslation('account');
```

但这个仓库里历史代码大量使用 `t('namespace:key')`，继续沿用即可。

## 新增命名空间的完整步骤

只有在“现有 namespace 明显不适合承载这批文案”时，才新增命名空间。

比如你新增了一个独立业务域 `teacher_report`，那完整步骤如下。

### 1. 新增翻译文件

新增 3 份文件：

- `public/locales/zh-CN/teacher_report.json`
- `public/locales/en/teacher_report.json`
- `public/locales/zh-Hant/teacher_report.json`

### 2. 注册 namespace 常量

修改：

- `public/locales/constants.ts`

把新 namespace 加进去。

### 3. 注册 i18n 类型

修改：

- `public/locales/i18next.d.ts`

你需要做两件事：

- import 新的 json 类型
- 在 `I18nNamespaces` 里补上新字段

### 4. 注册前端运行时加载列表

修改：

- `src/web/common/i18n/index.ts`

把新的 namespace 加到 `namespaces` 数组里。

如果这一步漏掉，运行时不会自动加载这个 json。

### 5. 再去页面里用 `t('teacher_report:xxx')`

这时才算完整接通。

## 推荐的 key 命名方式

### 推荐

推荐按“页面/模块/语义”组织：

```json
{
  "dashboard": {
    "title": "教学看板",
    "description": "汇总近期教学任务、作业状态和学生预警信息。"
  }
}
```

或者：

```json
{
  "auth": {
    "username": "用户名",
    "password": "密码",
    "submit": "登录"
  }
}
```

### 不推荐

不推荐把 key 写成自然语言：

```json
{
  "教学看板": "教学看板"
}
```

也不推荐把 key 写成只在当前页面才能看懂的缩写：

```json
{
  "ttl": "教学看板"
}
```

### 判断标准

一个好 key 应该满足：

- 不看 UI，也能大致知道它属于哪个模块
- 将来文案改了，key 不需要跟着改
- 同事第一次看到时，能猜出用途

## 动态文案怎么写

如果文案里带变量，不要手拼字符串，优先用插值。

### 推荐写法

json：

```json
{
  "summary": {
    "weeklyCourses": {
      "value": "{{value}} 节"
    }
  }
}
```

代码：

```tsx
t('dashboard.summary.weeklyCourses.value', { value: 18 });
```

### 不推荐写法

```tsx
`${count} 节`
```

原因：

- 不利于翻译
- 英文语序可能不同
- 后面想接其他语言会更麻烦

## 动态 key 的建议

这条非常重要。

在 TypeScript 里，动态 key 很容易把类型系统搞炸，尤其是 `react-i18next` 已经做了资源类型推导时。

### 尽量不要这样写

```tsx
t(`languageSwitcher.options.${option}`);
```

这类写法在编辑器里很容易报类型错误。

### 推荐这样写

```tsx
const localeLabelMap = {
  'zh-CN': 'languageSwitcher.options.zh-CN',
  en: 'languageSwitcher.options.en'
} as const;

t(localeLabelMap[locale]);
```

如果你在做状态映射、枚举映射、按钮映射，优先走“显式对象映射”。

## 教师端的特殊说明

教师端目前是一个独立的轻量方案，不和老页面强绑定。

你需要记住这几点。

### 1. 教师端当前只支持 2 种语言

当前支持：

- `zh-CN`
- `en`

如果你要给教师端补 `zh-Hant`，不能只加 json，还要同步修改：

- `src/app/teacher/components/TeacherI18nProvider.tsx`

里面的：

- `teacherLocales`
- 语言标准化逻辑

### 2. 教师端文案默认放 `teacher.json`

目前不要给教师端拆太多 namespace。

原因很简单：

- 现在教师端体量还不大
- 拆太早只会增加维护成本
- 同事更容易找到文案

建议：

- 教师端新增页面先统一放 `teacher`
- 只有教师端业务复杂到明显需要拆分时，再考虑分 namespace

### 3. 教师端页面最好写成业务块分组

例如：

```json
{
  "scores": {
    "title": "成绩管理",
    "export": "导出成绩"
  },
  "attendance": {
    "title": "考勤管理"
  }
}
```

比把所有 key 都挂在 `common` 下更容易维护。

## 不要依赖的错误直觉

下面这些是常见误解。

### 误解 1：只改 json 就够了

不一定。

如果你是：

- 改教师端已有 `teacher.json`

那通常够了。

但如果你是：

- 老页面新增 namespace

那一定不够，还要补注册文件。

### 误解 2：`next-i18next.config.js` 改了就会生效

对这个项目来说，不要这么理解。

当前这个包的前端实际运行时加载逻辑，主要看：

- `src/web/common/i18n/index.ts`
- `src/app/teacher/components/TeacherI18nProvider.tsx`

所以你日常改文案时，优先盯这两套实际运行代码，不要先去猜 `next-i18next.config.js`。

### 误解 3：英文可以以后再补

不推荐。

后补英文的结果通常是：

- 页面已经被其他同事接着改了
- key 已经散了
- 最后只能硬补，质量会明显下降

更好的做法是：

- 一次 PR 里把中文和英文一起补齐

## 提交前自查清单

每次改国际化，提交前至少看一遍这个清单。

- 有没有把硬编码中文直接写进 JSX
- 中文和英文是否都补了
- 老页面如果新增 namespace，注册文件是否都改了
- 文案 key 是否按模块组织，而不是零散命名
- 动态文案是否用了插值
- 动态 key 是否改成了显式映射
- 英文切换后 UI 是否溢出
- 刷新后语言是否保持

## 推荐工作流

如果你是在 vibe coding 节奏下快速改页面，建议按这个顺序。

### 场景 1：只是加几个按钮和标题

1. 先找对应 json
2. 补 `zh-CN`
3. 补 `en`
4. 页面里接 `t(...)`
5. 切中英文快速看一遍

### 场景 2：新增一个页面

1. 先决定归属哪个 namespace
2. 先把这个页面的核心文案结构写出来
3. 再开始写 JSX
4. 写完后切换英文检查长度和布局

### 场景 3：遇到 TS 对 `t(...)` 报错

优先检查：

1. 你是不是用了动态模板字符串 key
2. 你是不是没把新 namespace 注册到类型文件
3. 你是不是在教师端错误地用了老页面 namespace

## 可复制模板

### 教师端页面模板

```tsx
'use client';

import { Box, Heading, Text } from '@chakra-ui/react';
import { useTranslation } from 'react-i18next';

export default function DemoPage() {
  const { t } = useTranslation('teacher');

    <Box>

    </Box>
  );
```

### `teacher.json` 模板

```json
{

  }
```

## FAQ

### Q1：教师端能不能直接复用 `common`

能，但不建议作为默认方案。

原因：

- 教师端现在已经有独立 `teacher` 命名空间
- 继续往 `common` 塞教师端业务文案，会让边界越来越乱

默认规则仍然是：

- 教师端业务文案放 `teacher`
- 通用到全站都能复用的短词，才考虑放 `common`

### Q2：为什么我改了 json，页面没变

优先排查：

- 你改的是不是当前语言对应的文件
- 页面是不是用错了 namespace
- 老页面新增 namespace 时有没有注册
- 组件是不是还写着硬编码文案

### Q3：为什么切换英文后布局乱了

这是正常现象，不是国际化本身有问题。

英文通常比中文更长，所以每次加新文案后都要看：

- 按钮宽度
- 标题换行
- 表格列宽
- 卡片高度

## 最后一句建议

这套项目里的国际化开发，最稳的方式不是“想到哪改到哪”，而是：

先判断你在 `app/teacher` 还是 `pages`，再决定改哪个 namespace，最后一次性把多语言补齐。

如果你懒得想，默认按下面这条执行基本不会错：

- 教师端新需求：改 `teacher.json`
- 老页面新需求：先复用已有 namespace，不够再新建
